# SESAME 6 Pro 接続調査（2026-10-03）

## 実機で確認した事実

- Raspberry Pi Zero W / DietPi、Linux 6.18.39、BlueZ 5.82。
- Home Assistant 2025.11.3、Bleak 1.0.1、bleak-retry-connector 4.4.3。
- 「玄関ドア」は SESAME 6 Pro（model 21）、「エントランス」は Bot 3（model 35）。両方が同じ BLE セッションゲートを使用する。
- 2026-10-01〜02 の Recorder に玄関ドアの `unavailable` が22回記録され、いずれも約34〜38秒で復旧した。正常時も30秒ごとの状態取得に接続・切断を行う。
- `MemAvailable` は約212〜218 MiB、低電圧履歴は `throttled=0x0`。前回の `Errno 12` は再発しておらず、受信バッファの設定 `net.core.rmem_default=1048576` も維持されていた。
- 調査中にも問題が再現した。01:00:57 に玄関ドアの初回接続がサービス探索中に切断し、01:01:00 に2回目の接続が成功した。初期トークン通知を受け取った直後、認証・状態通知を待つ前に `SESAME disconnected before publishing status` を返した。

## 確認できた不具合と修正

`establish_connection` は同じセッション世代内で接続を再試行する。
失敗した試行からの切断コールバックが、接続確立前にも
`_notify_ready_event`、`_login_event`、`_status_event` をセットしていた。
そのため、再試行が成功しても古い切断通知で状態待機が解除され、
正常な接続をエラー扱いして切断していた。通知購読完了を待たずに
ログインを書き込む競合も起こり得た。

`client.py` の `_on_disconnect` は、セッション世代に加えて、
通知元のクライアントが現在の `_client` と同一であることを確認する。
接続確立前の失敗した試行と別クライアントからの遅延通知を無視し、
現在の接続が切れた場合は従来どおり待機中の処理を解除する。
物理操作コマンドの再送は追加していない。

継続確認で01:26:23に接続タイムアウト、01:26:54に BlueZ の
`status=11/SEGV` を記録し、01:26:56にサービスが自動復旧した。
別の通信失敗も起きるため、読み取り専用のポーリングに限り、
タイムアウトまたは状態受信前の切断で1回だけ新しい BLE セッションを開く。
試行間はアダプターを解放し、操作の優先制御を維持する。
認証拒否は再試行せず、2回とも失敗した場合は正常状態を装わずエラーを返す。

## 検証

- 修正前：失敗した接続試行を含む OS3 ポーリングと、別クライアントからの切断通知を再現する8ケースが失敗。通常のポーリング4ケースは成功。
- 最終修正後：全264テストが成功。単発失敗からの復旧、継続失敗の通知、認証拒否時の再試行禁止、操作による再試行中断を検証した。変更したクライアントとテストの Ruff、構文検査、バージョン整合性検査も成功。
- テスト用 Python 3.13 の一時環境に `requirements-test.txt` と、HA の USB コンポーネントが要求する `aiousbwatcher==1.1.1`、`pyserial==3.5` をインストールした。
- リポジトリ全体の Ruff は既存の `discovery.py` の `SIM105` で失敗する。今回の変更箇所には lint エラーはない。
- 最終版を配置して08:27に Home Assistant を再起動した。08:29:57から08:39:48まで、玄関ドア・エントランスとも17回のポーリングが全件成功し、失敗は0。玄関ドアは `locked`、電池電圧5.988 V、RSSI -51 dBmを取得した。物理操作は行っていない。
- 調査用の一時的なデバッグログ設定は元に戻し、認証用トークンをメモリ内で生成する一時診断スクリプトは削除した。最終診断結果は実機バックアップディレクトリの `final-verification.jsonl` に保存し、秘密鍵やデバイスIDを含めていない。
- 08:41の Bluetooth サービスの手動再起動に伴い、各機器で1回ずつ状態取得タイムアウトを記録した。その後、玄関ドアは08:42:51に `locked`、Bot 3の電池センサーは08:43:18に復旧した。玄関ドアの電池センサーは09:10:40にも5.964 Vを取得し、09:28時点で追加の状態取得エラーはなかった。クラッシュ記録用の作業ディレクトリが `/var/lib/bluetooth`、サービスが `active` であることも確認した。

## 確認範囲

修正は、再試行が成功した後の誤った状態取得中断を解消する。
最初の BLE 接続が失敗する電波・アダプター側の原因と、BlueZ の
SIGSEGV の内部原因までは確定していない。
実機の APT で BlueZ の導入版と候補版はともに `5.82-1.1+rpt2` だった。
コアダンプは残っていなかった。`core_pattern=core`、`LimitCORE=infinity`
だが、サービスには `ProtectSystem=strict` が設定されている。
`/etc/systemd/system/bluetooth.service.d/90-diagnostic-core-directory.conf`
で作業ディレクトリを既存の書き込み可能な `/var/lib/bluetooth` に設定し、
次のクラッシュで `/var/lib/bluetooth/core` にダンプを残せるようにした。
このディレクトリは root 専用の0700で、ダンプは同じファイル名を使用する。
復元はこの追加設定を削除し、`systemctl daemon-reload` と
`systemctl restart bluetooth` を実行する。
短時間の正常動作だけで、不定期な通信障害の完全な解消は断定できない。
施錠・解錠などの物理操作は検証に使用しない。
